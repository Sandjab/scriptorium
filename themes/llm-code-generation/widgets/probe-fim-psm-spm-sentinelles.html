La perte est gardée sur les trois segments, pas seulement sur le milieu : un document transformé continue d'entraîner la prédiction gauche-à-droite sur son préfixe et son suffixe (Bavarian et al. 2022, § 3). Le jeton <EOT> final apprend au modèle à signaler que la jonction avec le suffixe est faite ; à l'inférence, on échantillonne jusqu'à lui.

Ce que Bavarian et al. mesurent (§ 4.2) : six modèles entraînés sur 50 milliards de jetons avec des taux de 0, 25, 50, 75, 90 et 100 %. Jusqu'à 90 %, aucun effet notable sur la perte de test gauche-à-droite ; à 100 %, une dégradation. Leurs runs principaux emploient 50 % (moitié PSM, moitié SPM) ; Code Llama applique la transformation avec une probabilité de 0,9, moitié PSM, moitié SPM (§ 2.3). Le tirage ci-dessus est fixé pour l'illustration : le taux est une probabilité par document, le compte exact varie d'un lot à l'autre.

Le même empan, cette fois vide : le tokenizer de Code Llama accepte un jeton d'appel <FILL_ME>, le scinde en préfixe et suffixe, puis reconstruit le gabarit d'entraînement. Le modèle génère le milieu jusqu'à <EOT>.

Pourquoi deux gabarits : en SPM, ajouter des caractères au préfixe n'invalide pas les clés et valeurs déjà calculées pour le suffixe, puisque le suffixe est placé avant (Bavarian et al., § 3.1). C'est la motivation première de ce format ; l'avantage dépend de la charge réelle (une retouche du suffixe invalide, elle, le cache du préfixe).
