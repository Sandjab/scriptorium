TPLinker — schéma « handshaking »

Trois matrices token×token, une seule passe

Deux triplets chevauchants partagent la même paire d’entités, dans les deux sens : (New York, a_pour_maire, De Blasio) et (De Blasio, né_à, New York). TPLinker les encode entièrement par des liens entre paires de tokens : une matrice d’entités partagée (EH→ET) et, par type de relation, des liens de têtes (SH→OH) et de queues (ST→OT).

Triplets

E = span d’entité (tête→queue) H = tête sujet → tête objet T = queue sujet → queue objet  ·  ⇄ = lien replié (tag 2 : sens inversé)  ·  cellule vide = tag 0, la classe « no-relation »

Cliquez un triplet pour allumer ses cellules dans les trois matrices, ou une cellule pour voir à quel(s) triplet(s) elle contribue. Le bouton « Décoder » rejoue l’algorithme d’inférence pas à pas.

Décodage (lecture des matrices)

Le point clé : les trois matrices sortent du même encodage, en une seule étape de prédiction. L’inférence lit exactement ce que l’entraînement a supervisé — pas d’exposure bias — contrairement à un décodeur en cascade (sujet, puis relations, puis objets) où chaque étage consomme les sorties potentiellement fausses du précédent.
Comment lire ces matrices ?

Chaque matrice est indexée par les tokens de la phrase : la ligne donne le token source du lien, la colonne le token cible. EH→ET (entity head → entity tail) est partagée par toutes les relations : une cellule (i, j) marquée « E » signifie qu’un span d’entité commence au token i et finit au token j. Pour chaque type de relation, « H » relie la tête du sujet à la tête de l’objet (SH→OH) et « T » relie leurs queues (ST→OT). Un triplet = 2 cellules d’entités + 1 cellule H + 1 cellule T ; deux triplets peuvent donc réutiliser les mêmes cellules d’entités sans aucun conflit, ce qui traite naturellement les chevauchements (SEO/EPO) qui bloquent les schémas de séquence.

Dans l’article original (Wang et al., COLING 2020), chaque matrice est aplatie en ne gardant que le triangle supérieur (i ≤ j) : un lien qui « pointe en arrière », comme le SH→OH de né_à allant du token 4 vers le token 2, est rangé dans la cellule miroir (2, 4) avec le tag 2 (« ⇄ », sens inversé). La case à cocher ci-dessus montre ce repli : la moitié hachurée n’est jamais calculée.
